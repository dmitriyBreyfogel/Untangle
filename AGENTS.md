# Правила репозитория

## Контекст проекта

Это семестровая работа по объектно-ориентированному анализу и программированию: игра Untangle на Java + Swing. Главная цель проекта — не только рабочая игра, но и аккуратная демонстрация ООП, SOLID, инкапсуляции, расширяемости и понятного проектирования.

Код разделён на два основных модуля:

- `src/model` — модель, правила игры, уровни, узлы, рёбра и стратегии движения.
- `src/view` — Swing-интерфейс, панели, отрисовка, навигация и стратегии рендера узлов.
- `test/model` и `test/view` — JUnit 5 тесты, повторяющие структуру основных пакетов.

`Class_Diagram.asta` хранит диаграммы, но агент не должен редактировать этот файл без отдельной прямой просьбы.

## Приоритеты архитектуры

Модель считается сильной частью проекта: сохраняй её общий подход, особенно точку расширения через `MovementStrategy`. Предложения по улучшению модели допустимы, но менять её нужно осторожно и только при явной пользе.

Основная зона внимания — `view`. Его нужно упрощать, очищать от костылей и делать понятным для строгой защиты: отдельные классы должны иметь ясную ответственность, минимальный публичный API и очевидные зависимости.

Точки расширения обязательны к сохранению. Добавление новой стратегии движения или отрисовки должно выглядеть как добавление нового класса и минимальная регистрация, без переписывания существующей логики.

## Команды

- Открыть папку проекта в IntelliJ IDEA — проект подхватывается через `Untangle.iml`.
- Запустить `UntangleApplication` — основной запуск игры из IDE.
- `javac --release 24 -encoding UTF-8 -d out/production/untangle <исходники>` — ручная компиляция production-кода при необходимости.
- `java -cp out/production/untangle UntangleApplication` — запуск после ручной компиляции.

Проект использует Java 24 и обычную IntelliJ IDEA структуру с директориями `src` и `test`. Maven-сборка больше не является основным способом запуска.

## Стиль кода

Пиши на Java в стиле уже существующего кода: 4 пробела, `PascalCase` для классов, `lowerCamelCase` для методов и полей. Не добавляй комментарии в код вообще: код должен объясняться структурой, именами и тестами. Держи `public` и `protected` API минимальными. Дочерние классы не должны получать доступ к методам родителя, которые им не нужны. Не вводи наследование там, где достаточно композиции или стратегии.

Модель не должна зависеть от Swing. View не должен брать на себя игровые правила.

## Тестирование

После значимых изменений компилируй production-код и запускай тесты из IntelliJ IDEA. Тесты называй `*Test.java`, методы — описательно, например `startLoadsFirstLevel`. Все значения в аннотациях `@DisplayName` должны быть строго на русском языке. Для Swing-проверок используй существующие test helpers из `test/view`.

## Git и коммиты

Агент должен самостоятельно делать локальные атомарные коммиты от текущего git-пользователя. Все сообщения коммитов пиши на русском, в стиле истории проекта. Допустимы аккуратные теги, например `[view] Упрощена отрисовка игрового поля` или `[test] Добавлены проверки стратегий`.

Никогда не выполняй `git push` без отдельной прямой команды пользователя. Не смешивай несвязанные изменения в одном коммите. Перед коммитом проверяй `git status`, чтобы не захватить чужие или временные файлы.

## Правила работы агента

Делай только то, что запросил пользователь. Учитывай его явные предпочтения: сохранить удачные решения в `model`, бережно относиться к стратегиям движения, критически улучшать `view`, не трогать диаграмму классов без просьбы. Если изменение может существенно поменять архитектуру или публичные контракты, сначала объясни риск и предложи вариант.
